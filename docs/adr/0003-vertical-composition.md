## 背景
- 求められていること
  - 決定 5、6、8 と AC-27〜AC-31、AC-35 は、ウィジェットに一行を明朝の縦書きで出すことを求める。枠は W-1 が 172×76〜153×68pt、W-2 が 148〜170pt 四方。
  - 求められる組み：縦書き用の字、回す「ー」、行頭の禁則（追い出し）、欠けた字0字。
- 部品の制約
  - SwiftUI の Text には、縦組みの指定が見当たらない［推測。SDK の SwiftUI の宣言は全部は読んでいない］。
  - ウィジェットは、UIViewRepresentable で包んだ UIKit のビューを使えない（Apple の文書。「確かめたこと」の 1）。
- テストとアクセシビリティの条件
  - AC-28 は、組みの結果（列ごとの字と字の向き）と L を H22 で読む。L は、禁則の字のない25字の一行での1列の字数。
  - AC-99 は、読み上げを1つのまとまりにし、ラベルに縦書き用の字を入れないことを求める。
  - AC-102 は、ウィジェットの項目を返すまでを 0.5 秒以内にすることを求める。
- 同じ組みを使う場所
  - S-1（type.book.line。W3、Dynamic Type）
  - S-5 の見本（172×76pt）
  - H22（tech-lead r1 の提案5、決定 21）
- 拡張の分離
  - 拡張は ReadingCore だけを使う。既定の分離は nonisolated の見込みだった（ADR 0001。7-1 の申し送り）。

## 決定
- 組みは ReadingCore の純粋な関数（nonisolated、値の型は Sendable）にする。
  - 受け取るもの：一行と枠。
  - 返すもの：升目ごとに、元の字、出す字、回すか、ずらす量、列、行、位置。全体として、字の大きさ、L、列の数。
- 描くのは SwiftUI の Text だけにする。
  - Text を ZStack に置き、位置は frame、offset、rotationEffect だけで決める。
  - W-1、W-2、S-1、S-5、H22 は同じ View を使う。
- 字の置き換えとずらし
  - 縦書き用の字は、Unicode の縦書き用の字（U+FE11 など）に置き換える。
  - 「ー」「〜」「～」は 90 度回す。
  - 小さい仮名と回す字は、フォント（ヒラギノ明朝 ProN）の縦書き用の字形と同じ位置へ、字ごとにずらす。ずらす量は、組むときに Core Text で引いた字形の外枠から出す。
- 拡張のターゲットの既定の分離は nonisolated にする。

## 組みの手順と、入るかの式
### 手順
1. 字に分ける：前後の空白を除いた一行を、書記素（Character）に分ける（PRD 11 の冒頭）。
2. 縮める：ウィジェットと S-5 だけ、26字以上なら PRD の縮め方で25字までにする。足した「…」の升目は、元の字も「…」にする。S-1 は縮めない（AC-29）。
3. 縦にするかを決める：かなか漢字を1字も含まなければ横書きにする（AC-30）。かなと漢字の範囲は次のとおり。
   - U+3041〜309F、U+30A0〜30FF、U+31F0〜31FF、U+FF66〜FF9F
   - U+3400〜4DBF、U+4E00〜9FFF、U+F900〜FAFF、U+20000〜323AF
   - U+3005〜3007
4. 出す字を決める。
   - (a) 半角の印字できる字（U+0021〜007E）は、全角の字（U+FF01〜FF5E）に直す。一行の中の空白、タブ、改行は、全角の空白（U+3000）にする。
   - (b) 下の置き換えの表を当てる。
   - (c) 回す字と小さい仮名に印を付ける。
5. 列に分ける。
   - 1列の字数を L＝⌊A_h÷s⌋ にし、先頭から L 字ずつ列に分ける。
   - 次の列の先頭が行頭禁則の字なら、前の列の終わりの字を次の列へ送る。送った字も禁則の字なら、もう1字送る。
   - 前の列が1字だけになっても満たせないときは、送らない。
6. 入るかを見る：C×s＋(C−1)×0.25s ≤ A_w なら入る。C は 5 のあとの列の数。
7. 字の大きさを決める。
   - s を開始の値から 1pt ずつ 13pt まで下げ、最初に入った s を使う。
   - 13pt でも入らなければ、13pt で 5 の送りをせずに組み、kinsokuRelaxed を真にする。
   - 25字以下なら、送りなしで必ず入る。例：W-1 の小さい枠は C＝5 で 78pt ≤ 106pt。
8. 位置を決める。
   - 列 k（右から 0、1、…）の升目の左端：x＝(W−i)−(k+1)s−k×0.25s
   - 行 r の上端：y＝i＋r×s
   - Text は、箱の中心を升目の中心に合わせて置く。
   - ヒラギノ明朝 ProN の Text の箱は、13〜28pt で s×s だった（leading は入らない）。箱と em の枠が合うので、上下の補正は要らない（実測の差は 0.011em 以下）。

### 25字のときの結果
帯は実測の 43pt。組みの関数で、計算と同じ値が出た。

| 枠 | s | L | 列（送りなし） | 余り | 送りで列が1つ増えたとき |
|---|---|---|---|---|---|
| W-1 172×76 | 15 | 5 | 5 | 35.0 | 15pt のまま。余り 16.25 |
| W-1 153×68 | 13 | 5 | 5 | 28.0 | 13pt のまま。余り 11.75 |
| W-2 170 | 20 | 5 | 5 | 18.0 | 19pt に下がる（L＝6）。余り 0.25 |
| W-2 148 | 19 | 5 | 5 | 2.0 | 16pt に下がる（L＝6）。余り 0 |

- W-1 の字の大きさは、仕様 9 の値（15pt と 13pt）と同じ。
- 帯は推測の 38〜40pt より広い 43pt だった。そのため余りは、仕様の計算（例：172×76 は 40.0 と 21.25）より小さい。
- AC-27 の14字の一行は、W-1 のどちらの枠でも 17pt、L＝4、4列だった。
- 禁則の送りが多い一行も、W-1 の2つの枠で 6列で入り、kinsokuRelaxed にならなかった。
  - 「あ、」を12回くり返して「あ」を足した25字：送り5回。
  - 「ああ。」」を6回くり返して「あ」を足した25字：送り4回。

### S-1 と横書き
- S-1
  - 縮め方をかけない。s は type.book.line（28pt を .title に合わせて拡大縮小）の値のままにし、下げない。
  - 次のときは、横書きの Text にする（決定 7）。
    - 列が A_w に入らない。
    - 文字の大きさが accessibility1 以上。
  - S-1 の A_w と A_h（仕様の決定 64）：A_w＝画面の幅−32（左右の space.16 の内側。393pt で 361）、A_h＝⌊画面の高さ×0.4⌋（852pt で 340）。i＝B＝g＝R＝0 で、ページの「p.61」は場所の下。列は右上から組み、上にそろえる。28pt で1列12字（60字は5列）。375×667pt の画面の 34pt だけは、幅に入らず横書きになる（designer の計算）。
- 横書き（AC-30）
  - 同じ列の場所に Text を1つ置く（W-1 は帯を残す）。
  - 開始の s から、minimumScaleFactor で 13pt まで縮める。

## 小さい仮名と回す字のずらし
- 比べた2つの道
  - フォントの縦書きの置き換えを、Text に任せる道
    - SwiftUI の Text には、縦組みの属性を渡せない［推測］。
    - フォントの記述子で、AAT の type 4（selector 0）か OpenType の vert を強めた。横組みの Core Text の行では、22字のうち0字しか置き換わらなかった。
  - Core Text の kCTVerticalFormsAttributeName を付けた行で引く道
    - 22字とも置き換わった（W3、W6）。
    - 置き換わった字形は形が同じで（外枠の大きさの差は 0.001em 以下）、位置だけが違う。
- 決めたこと
  - 手でずらす。ずらす量は字ごとに、縦書き用の字形の外枠の中心と、横書きの字形の外枠の中心の差にする。
  - 量は組むときに Core Text で引く。表を手で持たない。
- 測った差（右へ、上へ）
  - W6：右へ 0.089〜0.164em、上へ 0.083〜0.143em
  - W3：右へ 0.094〜0.158em、上へ 0.074〜0.135em
- 平均の値を1つ使う案は採らない。
  - W6 の平均（右へ 0.114em、上へ 0.104em）でずらすと、17pt で 0.44pt までずれた（っ 0.39pt、ャ 0.44pt）。
  - 字ごとの値にすれば、このずれはなくなる見込み［推測］。字ごとの値で描いて測ってはいない。ずらさない字の置き場所は、0.08pt 以内で合った。
- 回す字
  - 「ー」は、ただ回すと、フォントの縦書き用の字形より 0.05em 右に出る（W6）。回したあと、同じ方法で合わせる。
  - 「〜」の差は 0.005em だった。
- Core Text の使い場所
  - Core Text は Apple のフレームワークで、拡張でも使える見込み［推測］。拡張のターゲットで Core Text を呼ぶビルドは、まだしていない（7-4 で ios-engineer の最初のビルドで確かめる）。
  - 1回の組みで引くのは、多くて25字。

## 読み上げ（AC-99）
- ウィジェットの根に、.accessibilityElement(children: .ignore) と、PRD の形のラベルを付ける。
  - ラベルの中身：書名、ページ、保存した一行。縦書き用の字は使わない。
- spike の結果
  - VoiceOver と同じたどり方（要素になったところで止まる）では、要素は1つ。ラベルは「羅生門、61ページ。下人は、雨やみを待っていた。」だった。
  - XCUITest も、識別子 widget.rectangular の要素を1つだけ見つけた。ラベルは同じ。
  - ただし、XCUITest が読む自動化の木（automationElements）には、子の Text が15個残る（升目14個と「p.61」）。
- だから、まとまりの数を XCUITest の子の数で数えない。
  - H22 が、VoiceOver と同じたどり方で数えた数を返す（7-4）。
  - 本物の VoiceOver での読み上げは、G4-13 で見る。

## H22 の口
- アプリは ReadingCore を読み込み、ウィジェットと同じ View（W-1 の View、W-2 の View）を描けた。
  - 窓の中に描けた（UI テスト）。
  - ImageRenderer でも描けた（spike の sheet.png）。
- H22 は、テストの構成でだけこの口を使う（ADR 0005）。
- H22 が返す組みの結果（7-4 で contracts/ に書く形の案）
  - 枠：ファミリー、W、H、i、B、g、R
  - 字の大きさ s
  - L（この一行の1列の字数）と referenceL（禁則の字のない25字での L。AC-28 の L）
  - 列の数、送りの回数、kinsokuRelaxed、横の余りと縦の余り、向き（vertical か horizontal）
  - 出した字の並び（縮め方のあと）と、縮めたか
  - 升目ごと：元の字、出す字、回す角度、ずらす量（dx、dy。pt）、列、行、x、y
  - ページの文字（p.61）と場所
  - 読み上げのラベルと、まとまりの数
  - 押したときの URL（contracts/entry-urls.md）、見た目の id
  - 状態：normal、noLine、noLineNoPage、hidden、empty、unavailable

## 拡張の分離
- 拡張のターゲットの既定の分離は nonisolated（Swift の既定）にする。
- 理由：iOS 27.1 SDK の宣言では、TimelineProvider の要件はどの actor にも属さない。getSnapshot と getTimeline の completion は @Sendable。
- spike で確かめたこと
  - nonisolated で、Swift 6 の言語モード、並行性の検査は完全、警告をエラーにして、ビルドが通った。コンパイラーの警告は0件。
  - MainActor にした変種も、ビルドは通った。ただし、その設定が拡張のコンパイルに渡ったかを、ログで特定できていない［未確認］。
- MainActor を選ばない理由：MainActor にすると、WidgetKit が要件を呼ぶときに main actor の上にいることが前提になる［推測］。

## ロック中の写しの読み込み
- シミュレーターでは、保護の等級が効かない。spike で書いた写しの保護の属性は、nil と読めた。
- ロック中に拡張が写しを読めるかは、G4-1 で見る（ADR 0002 と同じ）。

## いちばん強い反論と、それでも選んだ理由
- 反論
  - 自前の組みは、OS の文字組み（字詰め、合字、異体字、縦書き用の字形の選び方）を捨てる。
  - 表にない字は崩れうる。「：」は縦書き用の字形がないので立てたまま、絵文字や結合文字は升目の中央に立てるだけになる。
  - 組みのコードと表を自分で持ち続けることになる。Core Text に任せれば、縦書き用の字形を OS が正しく選ぶ。
- それでも A を選んだ理由
  - AC-28 と H22 は、字ごとの結果と L を、描いたものと同じ組みから読むことを求める。Core Text の改行と禁則は、その決まりに合わせられない（案 B）。
  - 崩れうるのは、表にない字が出す形だけで、字が欠けることはない。升目は書記素で切るので、結合文字と異体字セレクタは1升目の中に残る。
  - 表は20行で、表で使う縦書き用の字形がすべてフォントにあることを確かめた。
  - 小さい仮名と「ー」の位置も、手の数値ではなく、組むときにフォントから引く。OS の縦組みと同じ字形の位置に合わせられる。
  - 崩れが見つかったら、表に行を足して直せる。保存の形は変わらない。

## 結果
- これで楽になること
  - W-1、W-2、S-1、S-5、H22 が同じ関数と View を使う。テストで読む組みと、画面に出る組みが同じになる。
  - 組みは純粋な関数なので、単体テストで決まった値（L、列、出す字）を比べられる。
  - 1回の組みは 0.045ms（Debug、シミュレーター）で、AC-102 の 0.5 秒に比べて十分小さい。
- これで難しくなること、守り続けること
  - 置き換えの表と禁則の字は、tokens.md（designer）とこの ADR の2か所にある。変えるときは designer が tokens.md を直し、tech-lead がここを直す。
  - 小さい仮名と「ー」のずらしは、ヒラギノ明朝 ProN の縦書き用の字形に頼る。iOS の更新でフォントが変わったら、単体テストで気づけるようにする。単体テストは、ずらした量が 0 でないことと、升目からはみ出さないことを見る。
  - XCUITest の自動化の木に子の Text が残る。受け入れテストでは、まとまりの数を H22 の値で見る。
  - 本物のウィジェット（システムが描く）での見え方は、まだ見ていない。G4-1 と G4-3 で見る。
- 元に戻すときの手順と手間
  - 描く View だけを案 C か案 B に替える。組みの関数、写し、保存の形はそのまま使える。
  - H22 の組みの結果のうち、描き方に関わる項目（ずらす量、位置）と、ウィジェットのスクリーンショットのテストを直す。
  - 手間は中（2〜3日［推測］）。
