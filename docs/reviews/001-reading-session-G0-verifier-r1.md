### 2. 名指しで判断した点

**(a) AC-10、AC-11、AC-13、AC-17：実時間を待たずに確かめられるか**

結論：H4（起動のときに時刻を固定する）と H5（起動したまま、とくにアプリが後ろにいる間に時刻を進める）があれば、待たずに確かめられます。
- AC-11：H4 だけで足ります。T0 で読み始め、terminate し（ヘッダーに「SIGKILL」とあります）、H4 を T0＋600秒にして launch し、終えると10分です。
- AC-13：H4 で固定し、H5 で750秒進めます。
- AC-17：H4 を 2026-10-15T23:50+09:00 にし、H5 で1800秒進め、H6 でタイムゾーンを固定します。
- AC-10：H5 の値は、アプリが前面に戻る前に変わる形でなければなりません。URL で前面に出してから進める形だと、「後ろにいる間は数えない」作り（O-1 の不具合そのもの）でも10分になり、不具合を見逃します。
- 限り：にせの時計は本物の時計を置き換えます。そのため「端末が眠ると止まる時計を使った」不具合は、シミュレーターでは見つかりません（仕組みからの判断で、動かしてはいません）。これは実機（G4）でしか見えません。
- 実時間で10分待つのは sleep と同じで、G3 の決まりに反します。

**(b) AC-12：だれが、どの手順と証拠で決めるか**

- シミュレーターでは決められません。
  - XCUITest の公開のボタンにロックはありません（Apple の技術者も、横のボタンの API はなく、近いのは home だと回答しています）。
  - simctl にもロックと自動ロックの操作はありません。
  - G3 で決められる代わりは、H9 で「読書中に `isIdleTimerDisabled` が偽」を読むことです。Apple の文書では、この値の既定は偽で、真にすると眠りを止めます。ただし PRD にそう書かない限り、これで合否を決めるのは Then の読み替えになります。
- 実機での確認は Takuma が行います（gates.md:106）。手順の案は次のとおりです。
  1. 最低対応の機種に、TestFlight か Release のビルドを入れる。Xcode のデバッガはつながない。
  2. 自動ロックを30秒にし、Face ID の画面注視認識機能をオフにする（見ていると画面が暗くならないため）。
  3. 本 A で「読む」を押した時を0秒とし、端末を机に置いて触れない。別の端末で、画面と秒の出る時計を一緒に録画する。
  4. 合格の線：40秒以内に画面が消える。1分後にロックを外すと、本 A の読書中の画面が出ている。終えると記録が1件で、分数は読み始めから終えるまでの分（±1分）。
  5. 証拠：録画（evidence/AC12_実機.mov）、記録の一覧のスクリーンショット、機種、iOS の版、ビルド番号。3回行う。
- G3 で verifier が実機を使えないなら、今の書き方では AC-12 は未検証になり、G3 は通りません（gates.md:65、:67）。だから重大1で、G3 と G4 を分けて書くよう求めました。

**(c) AC-14：XCUITest で再試行なしに0.5秒を安定して測れるか**

- 測れません。理由は3つです。
  - 操作の前に「Wait for app to idle」の段が入ります（フォーラムのログ）。
  - クエリにも時間がかかります。
  - CI のシミュレーターの揺れは、0.5秒に比べて大きくなります。
- 性能テスト（measure）は、端末ごとの基準値より悪くなったら落ちる仕組みです（Apple の文書）。0.5秒という絶対の線の合否には向きません。
- 安定させる案：H10 でアプリの中の区間を測り、テストはその値が500ミリ秒以下かを読みます（要修正9）。

**(d) AC-23：シミュレーターで通信のない状態を作れるか**

- 機内モードは作れません。
  - simctl に通信の操作がありません。status_bar は表示を上書きするだけです。
  - シミュレーターは Mac の通信を使います。
  - Network Link Conditioner は Mac 全体の設定で、テストごとに切り替えられません（利用者の報告）。
- G3 の代わりは H8 です。Q4 が (a)（イベントを送らない）なら、アプリに通信のコードがないので、流れを最後まで通して alert 0 を見るだけです。
- 本物の機内モードは実機で確かめます。手順に「機内モードをオンにし、Wi‑Fi もオフであることを確かめる」を入れます（機内モードでも Wi‑Fi が点いたままのことがあるため）。

**(e) AC-10：「ロック」と「ほかのアプリに移る」を XCUITest で起こせるか**

- ほかのアプリに移る：起こせます。`XCUIApplication(bundleIdentifier: "com.apple.Preferences").activate()` で移り、`app.activate()` で戻ります（activate は動いているアプリを終わらせません）。`press(.home)` でも移れます。
- ロック：公開 API はありません。
  - XCUIAutomation の中に非公開の `pressLockButton` の記号はありますが、Apple の支えのない API で、版が変わると壊れうるものです。
  - 使えたとしても、シミュレーターでのロックはアプリから見れば「後ろに回る」と同じです。端末の眠りやデータの保護は再現しません（仕組みからの判断）。
  - G3 は「後ろに回す」で代え、ロックそのものは実機に回すのがよいと考えます。

**(f) AC-24：許可のダイアログ0回をどう数えるか**

1. テストの前に `xcrun simctl erase`（か uninstall）で端末を消します。通知の許可は resetAuthorizationStatus(for:) の対象（XCUIProtectedResource）になく、simctl privacy の対象にもないからです。消さないと、前のテストの答えが残ってダイアログが出ず、0回と数えてしまいます。
2. 起動、追加の画面、加えた後、読み始めた後、終えた後のそれぞれで、`springboard.alerts.count == 0` と `app.alerts.count == 0` を確かめます。
3. 最後の手順の後は、決まった秒数だけ springboard の alert を待ち、出ないことを確かめます。
4. 割り込みの監視（addUIInterruptionMonitor）だけでは数えられません。ヘッダーに「Monitors are not invoked simply by the appearance of an alert」とあり、ダイアログが出ただけでは呼ばれないためです。
5. サインインの画面が0回であることは、出た画面の順が設計どおり（一覧、追加、一覧、読書中、終わり）であることで確かめます。

端末を消すので、このテストはランダム順の実行とは別の実行にします。

**(g) 仮の文言キーは合否に影響するか**

条件付きで、影響しません。条件は3つです。
- design/ の7章に、PRD の仮のキーと決めたキーの対応表と、日英の文がある。
- design/ の6章に、その文を出す要素の識別子がある。

- AC-7 の確認がシステムの確認画面だと識別子を付けられないことがあるので、その場合は「3」を入れた文が一致するかで見ます。
- PRD の書き方については提案13を見てください。
