## 1. 結論と推す案

**推す案：案6「本から写す、要る時に」（表紙で始め、ページで挟み、奥付で閉じる）**

「登録」という作業をなくします。本の情報は、次の2つがそろう時にだけ、手元の本から写します。
- 本のその部分が、もう手にある。
- 写すと、その場で見返りがある。

アプリ全体を「写して、押す」という1つの手つきでそろえます。

- **始まり（本を加える）**
  - 表紙か背を写し、書名の行を押します。著者の行も押せます。
  - 手で打つ道は、同じ画面に置きます。
  - 「名前はあとで」でも、今夜から始められます。その本は「今の本」と出ます（決定 66）。
  - バーコードは使いません。
- **毎晩**：今のままです（止めたページを写して一行を選ぶ、手で入れる、ページ数だけ、あとで）。本の情報は1つも聞きません。
- **終わり（読み終えた夜）**
  - 手元の本の最後にある奥付を写します。規則で欄を先に埋め、違う行は押して直します。
  - 写したものが、その夜の奥付（著者、出版社とレーベル、この版の年、受賞）になります。
  - 飛ばしてもよく、あとで本の画面から写せます。
- **積読**
  - 1冊ずつは、表紙を写します。
  - 何冊もまとめるときは、積読の山か棚の背を1枚写し、背ごとの行を押して加えます。v1.0 に入れるのは、写真1枚の確かめ（6-3 の V-1）で線に届いたときだけです。届かなければ、表紙を1冊ずつ写す形で出します。
  - 読み終えた夜に積読が0冊なら、その空の画面から写せます。
- 書誌のための通信は0件です。外部の API、書誌データの同梱、端末の AI で欄に振り分ける形は使いません。

**いちばん強い反論**
- **F を3つに分けただけに見えるおそれ。** 写す場面が1つから3つに増えます。gradual engagement を唱えた Wroblewski 自身が、"Avoid gradual engagement solutions that simply distribute the various input fields in a sign-up form across multiple pages." と書いています［公開情報 https://alistapart.com/article/signupforms ］。
- **奥付が F より薄くなるおそれ。**
  - 読み終えた夜は余韻の時間で、カメラの作業は飛ばされやすいです［推測］。
  - 飛ばされると、Takuma が名指しした出版社の行が出ません。F は加える時に奥付を写します。
- **自動では埋まりません。** これは F と同じです。見た読書アプリは、どれもバーコードで書名が出ます（docs/reviews/001-reading-session-biblio-alt-pdm.md の 4）。
- **積読の山の道は、同じ技で★1が集まる所です。**
  - Shelf Scanner（US、評価263）のレビューです［公開情報 https://itunes.apple.com/us/rss/customerreviews/page=1/id=6503261472/sortby=mostrecent/json ］。
    - 「It misidentified every single one.」（2025-01-18 ★1）
    - 「Shows no books can be identified, but if I pull them out and use the barcode feature, it can find them.」（2025-06-03 ★1）
  - 本物の棚でどれだけ読めるかは、まだ誰も確かめていません。
- **作る量は F より増える見込みです。** AC の差し引きは +2〜5 の見当で、F は −0〜3 でした［推測］。

**それでも推す理由**
1. **3つの場面は、どれもその場で見返りがあります。** 欄を分けただけではありません。
   - 表紙を写す → 今夜のしおりの画面とロック画面に、その本が出ます。
   - 奥付を写す → その夜の奥付になります（AC-77 そのもの）。
   - 積読の山を写す → その場で次の1冊が並びます。
   - Wroblewski の例でも、名前とメールを聞くのは "only when you want to publish or share" のときです［公開情報 同じ URL］。
2. **書く時期が、紙の読書ノートと同じです。** 新潮文庫『ほんのきろく』は、「本書には、書名、著者名、出版社名、読了日などの項目があらかじめ用意されていますので、本を一冊読み終えるごとに項目を埋め、読書記録をつけていきます。」という形です［公開情報 https://www.shinchosha.co.jp/bunko/blog/2021/07/15_3.html ］。欄は、このアプリの奥付とほぼ同じです。
3. **最初の夜までの手間が減ります。**
   - 1冊目にかかる時間です［推測。designer の秒の置き方］。
     - F：15〜25秒
     - 表紙を写す：5〜8秒
     - 「名前はあとで」：約2秒
   - HIG も "Postpone nonessential setup flows or customization steps. Provide reasonable default settings so most people can immediately start interacting with your app or game without performing additional configuration." と書いています［公開情報 https://developer.apple.com/design/human-interface-guidelines/onboarding 。JSON で読んだ］。
   - 最初の読書の到達率（I-1）に効きます。
4. **結末が目に入るおそれが消えます。** F では、加える時に奥付を開くので、このおそれがありました（designer の報告）。案6では、読み終えてから開きます。
5. **どれも飛ばせ、飛ばしても壊れません。**
   - 名前がなければ「今の本」と出ます（決定 66）。
   - 奥付の行がなければ、その行を出しません（AC-18）。
   - 理由がなければ「積読から」と出ます（AC-80）。
6. **「見つからない」と「違う本」が、仕組みの上で起きません。**
   - アプリは本を見分けません。読めた字を見せて、利用者に押させます。
   - Shelf Scanner の取り違えは起きません。ただ、読めないことは起きます。
7. **10秒で話せます。** 「表紙で始め、ページで挟み、奥付で閉じる。本がそのままデータになる」。奥付を撮るアプリは、前の調べもの（pdm と designer）で見つかっていません。

**作らない場合（F のまま）に起きること**
- 外部の API なしで出せます。
- ただし、バーコードと奥付を加える時に済ませるので、1冊 12〜20秒、積読10冊 2.5〜4分のままです［推測。designer の表］。
- 最初の1冊でも奥付を開くので、結末が目に入るおそれが残ります。
- バーコードを読んでも書名が出ないので、ほかのアプリに慣れた人は戸惑います（designer の表の D）。

**考えを変える条件**（線は［推測］）
- V-2（表紙）で、書名を押すだけで入る本が10冊中5冊以下なら：写す道を従にし、案4（打つ。受賞の一覧から著者の候補を出す）を主に見せます。
- V-4（聞き取り）で、「読み始める前に記録した」人が5人中3人以上なら：奥付を加える時にも写せる道を足します。
- tech-lead の見積もりで案6が F より2日以上重ければ：積読の山の道を v1.1 に回します。

### 2-1 機能ごとの表

- 加える時に、全部そろっていなくてよいもの：著者、出版社、レーベル、出版年、ISBN。今の本1冊なら、書名も要りません。
- なくてもよいもの：ISBN、出版年、レーベル。レーベルが効くのは「同じレーベル」の理由だけで、本を選ぶ理由の上位12に出版社とレーベルは入りません［公開情報 E-5］。
- 最後には要るもの：書名。読み終えた夜までに要ります（カードと本棚のため）。
- 出版社は「なくてもよい」側です。ただ、Takuma が名指しした4つの1つ（2026-10-18。docs/approvals/001-reading-session-G0-Q8.md）なので、奥付を写す場面で集めます。

### 2-2 Job から見直す

- **本の情報を入れる作業は、中心の Job の外にある準備です。**
  - Job の場面（夜、手がスマホに伸びかけたとき）で要るのは、「どの本の、どこから」です。
  - 「どこから」は、一行とページです。
  - 「どの本」は、手元の紙の本そのものです。紙のしおりは、本の名前を知らなくても続きを守ります［推測］。
- **本の情報が Job に効くのは、2か所だけです。**
  1. 最初の夜までの準備（I-1）。短いほどよいです。
  2. 読み終えた夜の「次の本のはじめ」（I-3）。次の本に移るのが速いほどよいです。理由の厚み（同じ著者など）は、その次です。選び方のつまずきは 3.6%（E-2）と小さいからです［公開情報］。
- **「登録」をなくすか後ろに回したときの、4つの力**

| 力 | F（加える時に全部） | 案6（要る時に本から） |
|---|---|---|
| 押し | 変わらない（スマホ 43.6%、疲れ 38.9%。E-1） | 同じ |
| 引き | 通信しない安心 | それに加えて、今夜から始められる（表紙1枚か0秒）。読み終えた夜に「自分の一冊の奥付」が残る［推測］ |
| 不安 | 加える時の手間と、読み取りの精度。結末が目に入る | 名前のない本が並ぶ。読み終えた夜の作業が増える。山の写真での取り違え |
| 習慣 | バーコードで全部出る、ほかのアプリに慣れている | 同じ。紙の読書ノートを読み終えた時に書く習慣とは合う |

- **不安と習慣を下げる手当て**（AC か design に入れる）
  - どの写す画面にも、手で入れる道を同じ所に置きます。読み取りを待つ間も押せるようにします（AC-94 の型）。
  - 「名前はあとで」で始められます。奥付は飛ばせ、あとで写せます。
  - カメラをバーコードに向けたら、「本の名前は表紙から写します」と出します（形は designer）。
  - 最初の画面に、「本の名前は表紙から写します。どこにも送りません」と1行で書きます（形は designer。言い方は reviewer が確かめる）。

### 3-3 考えたが捨てた案（理由を1行ずつ）
- **毎晩のページの写真の柱（ページの端にある書名）から、書名を拾う。** 柱に書名がない本が多い見込みです［推測］。選ばなかった列の字を残さない決まり（AC-69）ともぶつかります。
- **書店の Web ページを共有して加える。** 手元にない欲しい本には効きます。ただ、芯は手元の紙の本なので、後の版の候補にします。
- **声で書名を言う。** 夜の静けさに合いません［推測］。キーボードの音声入力は OS の機能なので、手で入れる欄でいつでも使えます。
- **端末の AI で、読んだ行を欄に振り分ける。** 規則より正しくならず、使える機種も約4〜5割です（tech-lead の spike）。

## 6. PRD への影響と、足す確かめ

### 6-1 AC（見当。直すのは pdm、判定は verifier と tech-lead）
- **外す（8）**：AC-4、AC-5、AC-6（書名で探す）、AC-9、AC-10、AC-11、AC-113（通信と問い合わせ）、AC-93（書誌の出どころの表示）
- **中身を替える（5）**
  - AC-2：バーコード → 表紙を写して書名の行を押す。
  - AC-3：続けて読む → 積読の山か「加えて次へ」。重なりは、そろえた書名で除く。

  - AC-103：外に送るのは書誌の問い合わせだけ → 外への要求は0件。
- **Given か Then を直す（2）**
  - AC-77：読み終えた夜に、奥付を写す道を先に出す。写さなければ、今ある値で奥付を出す。

- **足す（10〜13）**
  1. 表紙を写して書名の行を押すと、今の本になる
  2. 著者の行も押せる。別の行に替えられる。崩れた字を直せる（AC-66、AC-67 の型。1つにまとめてもよい）
  3. 名前はあとで（書名のない今の本）
  4. 書名のない本に、本棚から名前を付ける
  5. 読み終えた夜に奥付を写すと、規則で欄が先に埋まる
  6. 奥付を写さずに進める。あとで本の画面から写せる
  7. 写して何も読めないとき（AC-68 の型。表紙、奥付、山）
  8. 積読の山を写して、何冊も加える（条件つき。V-1 の線に届いたときだけ）
  9. 重なり（そろえた書名が同じ本）を加えない
  10. 写真を残さない（AC-69 を、表紙、奥付、山に広げる）
  11. 読み取りを待つ間も、手で入れられる（AC-94 を広げる）
  12. 書名のない本を読み終えたとき、カードの前に書名を入れられる
  13. （任意）書名が受賞の一覧と合い、著者が空なら、一覧の著者を候補に出す

## 8. 未解決

**tech-lead に確かめてほしいこと**
- 表紙の読み取り：飾った字、横書きと縦書きの混ざり、帯の宣伝の字。DataScanner で表紙と奥付の行を押せるか（撮る道の部品を使い回せるか）。
- 積読の山
  - 背ごとにまとめる規則の精度（本が傾いている、隣と接している）。
  - 平積みの山で、背の字が横向きになるときの読み取り。
- iPhone での最初の読み取りの待ち（Mac では 24.84秒）。写す場面が3か所になるので、どこで先に温めておくか。
- 奥付の ISBN の行を、チェックの数字で確かめて残せるか。
- 作る量の差（案6 と F）：バーコードの部品と H20、H21 が要らなくなる分、写す場面が3か所になる分、山の道の分。
- ストアや画面に「通信しません」「どこにも送りません」と書けるか（StoreKit の購入や、OS の機能の通信の扱い）。reviewer にも確かめてほしいです。

**designer に確かめてほしいこと**
- 3つの写す場面を、同じ部品でどう作るか。それぞれの最初の1行の案内。
- 読み終えた夜の流れ（奥付を写す → 奥付 → 次の1冊 → カード）に、画面が1つ増えること。飛ばす道の置き方。
- 名前のない本の、本棚での見せ方と、名前を付ける道。
- カメラをバーコードに向けたときの案内。
- 積読の山の結果の並べ方（背ごと）と、VoiceOver、大きい文字での形。
- 奥付の「この版の出版年」に、発行、改版、刷のどの年を入れるか（designer の前の未解決）。刷を奥付に出すことは、範囲を増やさないため v1.0 には足しません。

**pdm が PRD で決めること**
- 名前のない本が今の本から外れたとき（本棚で別の本を今の本にしたとき）の扱い。
- 書名のない本を読み終えたときの、カードの扱い。
