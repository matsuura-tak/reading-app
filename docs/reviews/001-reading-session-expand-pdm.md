# デジタル書籍、レコメンド、バーコードでの一括取得を製品として考え直す（pdm の調べもの）

## 0. 全体の結論
1. **デジタル書籍**：v1.0 では3つを入れます。(a) 電子の本も本棚に入れる。(b) Kindle の端末や iPad で読む人は、今の「伏せて読む」をそのまま使う。(c) 同じ iPhone で読む人は伏せずに「読み始める」を押し、電子の本のアプリへ渡す（小さな形）。ただし10秒の話（ポートフォリオ、スクリーンショット1〜3枚、ADA）の主役は紙と伏せる動作のままにします。
2. **レコメンド**：v1.0 で、「おすすめ」と呼べる形を出します。積読からの1冊に加えて、「この著者のほかの作品」「シリーズの次」「同じ賞の前後の年」として、持っていない本も出します。理由は事実を1行で書きます。本当の「これを読んだ人は」は v2 にし、出す前に人数の線を決めます。
3. **バーコードでの一括取得**：「向ければ出る、なければ写す」を推します（書誌データの同梱に、写す道を組み合わせる形）。ただし、大きさと更新の手間は tech-lead の数字を見てから決めます。同梱のデータは、2 のレコメンドで持っていない本を出すための元データにもなります。
- **3つはつながっています。** 同梱のデータがあれば、バーコード、本棚の写真、奥付、レコメンドの4つがまとめて強くなります。なければ、持っていない本のおすすめは受賞の一覧から出すものだけです。
- **全体へのいちばん強い反論**
  - v1.0 は、全部を入れるだけでも 2.53〜3.59倍の速さが要ります［推測。docs/prd/001-reading-session.md の冒頭］。3つを足せば枠からさらにあふれます。
  - 毎月のデータ更新という、終わりのない保守が増えます。
  - 芯（毎晩の入口）から作る手が離れます。

## 1. デジタル書籍への対応

### 1-1 結論と推す形
- **推す形**：v1.0 では (a)＋(b)＋(c) の小さな形。(c) の自動の記録と、Kindle の蔵書の取り込みは v1.1 に回します。
  - **(a) 登録**
    - 本に「紙か電子か」を持たせます。
    - 進み具合はページか％で入れられます。
    - 一行は、電子の本のスクリーンショットから、撮る道と同じ部品で選びます。
    - 電子の本にも奥付のページがあることが多いので、「奥付で送る」もスクリーンショットでできる見込みです［推測］。
  - **(b) 別の端末**：伏せる道をそのまま使い、案内の文とストアの文で伝えます。作る手間はほぼ0です［推測］。
  - **(c) 小さな形**
    - ロック画面の一行を押すと、しおりの画面が開きます。
    - 電子の本のときは「読み始める」を主にし、押すと記録が始まり、電子の本のアプリへ渡します。
    - 本を指定して開けるか、アプリを開くだけになるかは tech-lead に確かめます。
    - 止め忘れには、今の PRD の上限の決まりを使います。
- **理由**
  - 本を読む人の約半分は、紙と電子の両方を使います。
  - 競合のレビューでは、「Kindle 本も登録したい」「電子と紙を一緒に見たい」が繰り返し出ます（1-4）。
  - 電子の本が本棚に入らないと、両方を読む人の記録と次の1冊が途中で切れます。読み終えた次の本が電子だと、I-3（本から本）も測れなくなります。
- **(d)（v1.1 に回す）を推さない理由**
  - Takuma が名指ししました。
  - 競合では、電子の本に対応しているのが当たり前になっています（Bookmory、私は積読家、ブクログ）。
- **お話を紙のままにする理由**
  - 同じ iPhone で読む人には、伏せる動作が成り立ちません。
  - 電子は、文字ものに限ると金額で約7%です（1-2）。

## 2. レコメンドのニーズ

### 2-1 結論と推す形
- **v1.0 で「おすすめ」と呼べる形を出します。** 名前は「次の1冊」でも「おすすめ」でもよいです。ただ、「これを読んだ人は」とは書きません（product.md の 5 の決まり）。

## 3. バーコードでの一括取得（同梱の書誌データ。案 C）を製品として見直す

### 3-1 結論と推す形
- **推す形は「向ければ出る、なければ写す」です。**
  1. バーコードを続けて読むと、同梱のデータから書名、著者、出版社、レーベルが出ます。通信はしません。
  2. データにない本では、カメラはそのまま表紙を写す道に切り替わります。行き止まりはありません。
  3. 打つ道はいつも同じ画面に置きます。
  4. 本棚の写真の道（v1.0 に入れると決まった）も、読めた書名を同梱のデータに当てて、著者と出版社を候補に出せます。
  5. 「あとで」はそのまま残します。
- **条件**：tech-lead の数字で、次の2つを満たすこと。
  - アプリの大きさの増分が 100MB 以下［推測の線。下の 3-5 の研究の範囲（100MB 未満）に合わせた］。
  - 更新が、アプリの更新と一緒に年4回以内で済み、運用が1回0.5日以内［推測の線］。
- 満たさなければ、「写す」だけの今の推す案に戻します。

### 3-2 価値（数字）［推測。秒の置き方は rethink の designer と同じ］
| 道 | 1冊 | 積読10冊 | 新刊（出て1か月以内） | 電子の本 |
|---|---|---|---|---|
| 写すだけ（今の推す案） | 6〜10秒 | 約1〜1.5分 | 写せる | スクリーンショットから写せる |
| 国立国会図書館サーチ（A。もう使わない） | 数秒 | 40〜60秒 | 14日以内は5件中2件が0件 | 出ない |
| 同梱＋写す（推す） | 載っている本は2〜4秒、ない本は6〜10秒 | 20〜40秒（載っていれば） | 写す道に落ちる | ISBN がないことが多く、写す道に落ちる［推測］ |

- 「向けるだけで書名が出る」は当たり前の品質です。見た読書アプリは、どれもバーコードで書名が出ます（docs/reviews/001-reading-session-biblio-alt-pdm.md の 4）。
- 写すだけの形と比べて、積読10冊は約2〜3倍速くなる見込みです［推測］。

### 3-3 「申請」と「法的リスク」に当たるか（国立国会図書館の原文）
- 原文は ［公開情報 https://www.ndl.go.jp/data/data_service/quickguide 、2026-10-20 に WebFetch］です。
  - 「国立国会図書館が作成した書誌データ等（書誌データ・典拠データ・雑誌記事索引データ）は、営利・非営利の目的を問わず、どなたでも無償で利用することができます（*）。」
  - 「国立国会図書館が作成した書誌データ等を利用する際は出典の記載をお願いします。」
  - 「なお、個々の資料に付された⼀つ⼀つの書誌データ等に出典の表示を行う必要はありません。」
  - 「書誌データ等を編集・加工等して利用する場合は、上記出典の記載とは別に、編集・加工等を行ったことの記載もお願いいたします。なお、編集・加工等した情報を、あたかも国立国会図書館が作成したかのような態様で公表・利用しないでください。」
  - 「* 第三者（当館以外の者をいいます）が作成し…提供している書誌データ等については、出典の表示方法も含めてその提供元の定める利用条件に従ってください。」
  - 「※JAPAN/MARCの全件データも提供しています（申し込みが必要です）。」
- **読み方**
  - 利用の申請も許諾も要りません。営利でも使えます。
  - 求められるのは、次の3つです。
    - アプリのどこか1か所に出典と加工の記載を出す（本ごとには要らない）。
    - 国立国会図書館が作ったように見せない。
    - 第三者の書誌を混ぜない。
  - 使うときに利用者の書名や ISBN をどこにも送らないので、reviewer の K1（外部送信規律）の問いは起きません［推測。法律の判断は Takuma を通す］。
- **残る「申し込み」**
  - 全件のデータ（JAPAN/MARC）は、問い合わせのフォームから1回申し込みます。これは利用の許諾ではなく、データを送ってもらう頼みです。
  - Takuma がこれも「申請」と見るなら、申し込みの要らない取り方を tech-lead に確かめます（OAI-PMH の全件ファイルを国立国会図書館が作った書誌だけに絞る形）。
- **product.md のずれ**
  - 今の 5 は、書誌を「CC BY」と書いています。この quickguide のページには、CC BY の名前がありません（WebFetch の答え）。
  - 同梱にするなら、文を quickguide の条件に合わせて直します。

### 3-4 新刊の遅れと、写す道との組み合わせ
- 全国書誌は「出版物が国立国会図書館に届いてから約1か月後に提供」です［公開情報 https://www.ndl.go.jp/data/data_service/jnb 。biblio-alt-pdm の引用］。
- 毎週の JAPAN/MARC には、作成中の新着書誌は入りません［推測。biblio-alt-tech-lead の 4］。
- アプリの更新の間隔が加わるので、実際には1〜3か月遅れる見込みです［推測］。
- **いちばん欠けるのは、いちばん求められる本です。** 選ぶ理由の1位は「好きな作家の新刊」（32.0%）で、まさにデータにない本です。だから写す道は「予備」ではなく、新刊の主な道です。
- 「名前で迎え、奥付で送る」の写す部品は、そのまま残します。
- **組み合わせの決まり**（AC の見当）
  - 同梱のデータにあれば、自動で埋めます。
  - なければ、写す画面に切り替わり、「まだ載っていない本です」と出します（文言は designer）。
  - 写して入れた本は、次のデータの更新で ISBN が合えば、空の欄だけを埋めます。利用者が直した欄は上書きしません（作れるかは要確認）。

### 3-5 アプリの大きさが需要に与える影響
- 大きさと入れる率の関係で見つかったのは、Google Play の分析です。100MB 未満のアプリで、6MB 大きくなるごとに入れる率が約1%下がる相関でした［公開情報 https://medium.com/googleplaydev/shrinking-apks-growing-installs-5d3fcba23ce2 。2017年、Android、相関。検索の要約で、本文は開いていない］。
- iOS の公開の値は見つかりませんでした［推測］。
- 数十〜数百 MB を最初から入れると、入れる率が下がる向きに働きます［推測］。
- **避け方の案**（作れるかは tech-lead）
  - 最初に入れるのは、小さな芯の部分にします（例：文芸の分類、文庫と新書、最近の年に絞る）。
  - 残りは、初めて開いたあとに Apple から落とします（Background Assets）。利用者の書名は送りません。
- **確かめていないこと**：ストレージへの不満がレビューにどれだけあるか（見ていない）。

### 3-6 レコメンドへの効き
- 同梱のデータには、著者、シリーズと巻、レーベル（叢書）、分類、出版年が入る見込みです［推測。項目は tech-lead に要確認］。これで、2-3 の v1.0 の「持っていない本」（この著者のほかの作品、シリーズの次）が作れます。
- 同梱がなければ、持っていない本は受賞の一覧（3賞）からだけになります。

### 3-7 比べ
| 点 | 写すだけ | 同梱＋写す（推す） | 同梱だけ |
|---|---|---|---|
| 当たり前の品質（向ければ書名が出る） | 届かない | 載っている本で届く | 載っている本で届く |
| 新刊 | 写せる | 写せる | 出ない（行き止まり） |
| 電子の本 | スクリーンショットで写せる | 同じ | 出ない |
| 通信 | 0 | 0（後から落とすなら、Apple へのファイルの要求だけ） | 0 |
| 出典の表示 | 不要 | 1か所 | 1か所 |
| 保守 | なし | データの更新（年4回〜毎月） | 同じ |
| レコメンドの持っていない本 | 受賞の一覧だけ | 著者、シリーズ、賞 | 同じ |
| 10秒の話 | 「本がそのままデータになる」 | 「向ければ出る、なければ写す」（話としては弱くなる［推測］） | ー |

- **いちばん強い反論**
  - 大きさ、終わりのない更新、新刊に弱いこと。
  - 「データを持たない、通信しない」という単純な話を失います。
  - 写すだけでも積読10冊は約1〜1.5分で、そもそも10冊を一度に入れる人がどれだけいるかの証拠がありません。
- **作らない場合に起きること**：バーコードで書名が出ない読書アプリになります。ほかのアプリに慣れた人は戸惑い、「登録が重い」という不満が残ります（日本の3本では、星3以下の約2割が登録の失敗。product.md の 4）。

### 3-8 PRD と product.md で変わる所の見当
- **PRD**
  - バーコードの AC（AC-2、AC-3 の続けて読む形）を、同梱のデータの形で戻します。
  - AC を足します。
    - データにないときは写す道へ
    - データの版を設定の画面に出す
    - 出典と加工の記載を1か所に出す（AC-93 を quickguide の形に直す）
    - オフラインでも同じに動く
  - 12 の非機能要件：大きさの上限、データの引き当ての速さ（例：0.3秒以内［推測］）。
  - 6 の表に、データの遅れと大きさを足します。
  - 14 のガードレールに、Day 1 の継続率を足します（大きさの影響を見る）。
  - 17：外部送信の文を「通信しない」に直します。
- **product.md**
  - 5 の収益の形の書誌の文（CC BY）を、quickguide の条件に直します。
  - 版の地図の登録を「向ければ出る、なければ写す」にします。

## 4. Takuma に決めてほしいこと（答えで製品の形が変わるものだけ）
1. **本の情報の取り方を「向ければ出る、なければ写す」に変えるか**
   - 推奨：変える。ただし tech-lead の数字で、大きさの増分 100MB 以下と、更新の運用が年4回以内・1回0.5日以内に収まるときだけ（線は［推測］）。
   - いちばん強い反論：大きさと終わりのない更新が増え、いちばん求められる新刊にはどのみち効きません。「通信もデータも持たない」単純さを失います。
